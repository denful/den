# Den created aspects.

<Aside icon="nix" title="Nix Classes">

An aspect is an attrset that contains modules of different Nix `class`.

```nix
gaming = { nixos = ...; homeManager = ...; hjem = ...; darwin = ...; }
```

Such an attrset is an [**aspect**](https://dendrix.denful.dev/Dendritic.html) because it lets you configure a single cross-cutting concern (`gaming`) over different configuration domains.

Nix classes are NOT an artificial concept created by Den. There are [many nix classes in the wild](https://github.com/search?q=language%3ANix+%28%22+class+%3D+%22+AND+%22evalModules%22%29&type=code), the most common are [`nixos`](https://github.com/search?q=repo%3ANixOS%2Fnixpkgs+%22class+%3D+%5C%22nixos%5C%22%22&type=code), [`darwin`](https://github.com/nix-darwin/nix-darwin/blob/da529ac9e46f25ed5616fd634079a5f3c579135f/eval-config.nix#L81), [`homeManager`](https://github.com/nix-community/home-manager/blob/5be5d8245cbc7bc0c09fbb5f38f23f223c543f85/nixos/common.nix#L27).
</Aside>

Den **automatically** creates an aspect for each of your host/user/home defintions. For example, with the following definitions:

```nix "homeManager" "hjem" "maid" "x86_64-linux"
den.hosts.x86_64-linux.igloo.users = {
  tux = {
    classes = [ "homeManager" "hjem" ];
  };
  pingu = {
    classes = [ "maid" ];
  };
};
```

Den will create the following aspects for you, each with empty owned-config
keys for the entity's classes:

```nix "nixos" "homeManager" "hjem" "maid"
 den.aspects.igloo = {
   nixos = {}; # `host.class` was derived from the host platform
 };

 den.aspects.tux = {
   homeManager = {};
   hjem = {};
 };

 den.aspects.pingu = {
  maid = {};
 };
```

These are plain attrsets — the pipeline makes them context-aware
automatically. See [Parametric Aspects](/explanation/parametric/) for how
aspects receive `host`/`user`/`home` context.

## Aspect Basics

In addition to per-class modules, an aspect has an `includes` list referencing other aspects, and can hold nested aspects under keys of its own:

```nix
{ den, ... }: {
  den.aspects.laptop = {
    # Owned configs per class
    nixos = { pkgs, ... }: {
      environment.systemPackages = [ pkgs.git ];
    };
    darwin.nix-homebrew.enable = true;
    homeManager.programs.starship.enable = true;

    # Dependencies
    includes = [
      den.batteries.primary-user
      den.aspects.gaming.emulation
    ];
  };

  den.aspects.gaming = {
    darwin = ...;
    nixos = ...;
    emulation = {
      darwin = ...;
      nixos = ...;
    };
  };
}
```

## Owned Configs

Attributes named after a Nix class (`nixos`, `darwin`, `homeManager`, or any
custom class) are referred by this documentation as **owned configs**.

They are just a regular Nix module:

- **Attrset Module**: plain and simple configuration.
- **Function Module**: taking module arguments (`{ config, pkgs, lib, ... }: { }`).

```nix
# Attrset form
den.aspects.laptop.nixos.networking.hostName = "laptop";

# Function form
den.aspects.laptop.nixos = { pkgs, ... }: {
  environment.systemPackages = [ pkgs.git ];
};
```

## Includes

`includes` is a list of aspects used to declare dependencies between aspects.

Unlike other Nix libraries that use stringly-typed "tags" to define requirements,
Den uses real aspect references, these can be type-checked by the Nix module system.

```nix
den.aspects.workstation.includes = [
  # Reference another aspect (its full DAG is included)
  den.aspects.dev-tools
];
```

It is important to note the three kinds of values that Den distinguishes
as part of an includes list:

1. Static (plain attribute set): `{ nixos.foo = ...; }`
2. Static (aspects leaf): `{class, aspect-chain}: { ${class}.foo = ...; }`
3. Parametric (any other function): `{ host, user }: { ${host.class}.foo = ...; }`

`(1)` and `(2)` are termed *static aspects* and are the terminal leafs of aspects DAG.
`(1)` provides configuration unconditionally, and `(2)` gets access to the `class` that is
being resolved and an `aspect-chain` that lead to the current aspect (most recent last).


`(3)` is a more interesting kind of aspect that is used by Den to pass host/user defitions
into these functions, so they can inspect the host features and provide
configuration accordingly.


## Nested aspects

Any key on an aspect that is not a class key or a structural key (`includes`,
`excludes`, `meta`, `policies`, …) is a nested aspect, reachable as
`den.aspects.<aspect>.<name>`:

```nix
den.aspects.tools.editors = {
  homeManager.programs.helix.enable = true;
  homeManager.programs.vim.enable = true;
};

# Used elsewhere:
den.aspects.alice.includes = [ den.aspects.tools.editors ];
```

Nested aspects can also be parametric functions:

```nix
den.aspects.alice.work-vpn = { host, user, ... }:
  lib.optionalAttrs host.hasVpn {
    nixos.services.openvpn.servers.work.config = "...";
  };
```

`host.hasVpn` is an attribute you set on the host, not a built-in one; see
[Freeform attributes](/explanation/entities/#freeform-attributes).

Older configurations write `den.aspects.<aspect>.provides.<name>` (or
`._.<name>`). That nesting still works and yields the same aspect at
`den.aspects.<aspect>.<name>`, but it is legacy; write the direct form. The
cross-entity keys `to-users`, `to-hosts`, and `<host>` on a user aspect
(below) are the exception: they are read only from `provides`.

### Naming and inclusion

In `den.aspects.<path>`, every segment is a name you choose, nested to any
depth. This is a valid aspect:

```nix
den.aspects.foo.bar.baz.nixos = { config, ... }: { /* ... */ };
```

Declaring an aspect does not apply it. It reaches a host only when the host's
resolution tree includes it, by one of these routes:

```nix
# 1. From the host's own aspect
den.aspects.<host>.includes = [ den.aspects.foo.bar.baz ];

# 2. From a policy that injects it, activated somewhere in the tree
den.policies.<policy> = { host, ... }: [ (den.lib.policy.include den.aspects.foo.bar.baz) ];
den.schema.host.includes = [ den.policies.<policy> ];

# 3. For every host, through the host kind
den.schema.host.includes = [ den.aspects.foo.bar.baz ];

# 4. Globally, for every host, user, and home
den.default.includes = [ den.aspects.foo.bar.baz ];
```

Including a parent does not include its children. To include all of an
aspect's direct children at once, include `den.aspects.<aspect>._`:

```nix
den.aspects.foo = {
  nixos = { /* not included by foo._ */ };
  bar.nixos = { /* included */ };
  bar.baz.nixos = { /* not included: a grandchild */ };
};

den.aspects.<host>.includes = [ den.aspects.foo._ ];
```

`<aspect>._` includes each depth-1 child aspect, including legacy
`provides` children, and nothing else: not the aspect's own class keys, and
not grandchildren (use `den.aspects.foo.bar._` for those). The same `_` used
as an attribute path, as in `den.aspects.<aspect>._.<name>`, is the legacy
alias for `provides.<name>`.

## Cross-entity provides

Three special `provides` keys route configuration across entity boundaries.
They fire automatically during the tree walk — no manual policy wiring needed:

```nix
den.aspects.igloo = {
  # Deliver to ALL users on this host
  provides.to-users = { user, ... }: {
    homeManager.programs.helix.enable = user.name == "alice";
  };

  # Deliver to a specific user by name
  provides.alice.homeManager.programs.vim.enable = true;
};

den.aspects.tux = {
  # Deliver to ALL hosts this user lives on
  provides.to-hosts = { host, ... }: {
    nixos.programs.nh.enable = host.name == "igloo";
  };

  # Deliver to a specific host by name
  provides.igloo.nixos.programs.emacs.enable = true;
};
```

<Aside>
For new configurations, prefer `den.policies` with explicit `policy.include`
for cross-entity delivery — it's more flexible and explicit. The `provides`
patterns above are a permanent API for existing usage.
</Aside>

## Global Defaults

`den.default` is a special aspect applied to every host, user, and home:

```nix
{
  den.default = {
    nixos.system.stateVersion = "25.11";
    homeManager.home.stateVersion = "25.11";
    includes = [
      den.batteries.define-user
      den.batteries.inputs'
    ];
  };
}
```

To use flake inputs inside class modules (`inputs` as a module argument, an
input's NixOS module, home-manager `extraSpecialArgs`), see
[Flake inputs and specialArgs](/explanation/class-modules/#flake-inputs-and-specialargs).

<Aside type="caution">
Owned configs from `den.default` are deduplicated across pipeline stages, so
they land once. Parametric functions in `den.default.includes` are not: every
context stage whose context has the function's arguments calls it, and each
call is a separate instance. Dispatch goes by argument shape, and a context
matches when it has *at least* those arguments:

- `{ host }` runs in the host context **and** in every user context on that
  host, because a user context also carries `host`;
- `{ host, user }` runs only in user contexts.

A user context's `nixos`/`darwin`/`os` content also reaches its host
([#694](https://github.com/denful/den/issues/694)). So a `{ host }` function in
`den.default.includes` that sets host options lands once for the host plus once
per user, and an option that must be defined once (`boot.kernelPackages`, for
example) fails with "is defined multiple times". To deliver host content once:

- put host-only parametric aspects in `den.schema.host.includes`, or
- keep the aspect static and take `host` in the class module:
  `nixos = { host, ... }: { … };`.

Write your includes as bare functions — no extra wrapper is needed.
(`den.lib.take.exactly` is deprecated.)
</Aside>

## Aspect Meta-Data

Aspects have a `meta` submodule that can be used to attach meta-data
at the aspect-level.

This is useful for [introspection, for example](https://github.com/denful/den/commit/809834982bb92e77228c91b9c24be8b17c06dfd3), using some key to filter out aspects
or communicate information about aspects to other tooling like graph generators.

Since `.meta` is a freeformType you can add any custom attribute or import a module on it.

The following are default `meta.*` attributes defined by Den:

```nix
aspect.name # "igloo", the submodule name
aspect.meta.loc   # the location [ "den" "aspects" "igloo" ] from where name is derived.
aspect.meta.name  # "den.aspects.igloo" derived from loc
aspect.meta.file  # the last file where this aspect was defined.
aspect.meta.self  # a reference to the aspect module `config`.
```

You can access meta values by referencing an aspect:

```nix
den.aspects.igloo.meta.name
```

Or if an aspect needs to access its own meta data as part of its parametric functor,
it can do something like:

```nix
den.aspects.foo =
  { config, lib, ... }: # module args to access `config.meta`
  {
    meta.foo = "bar";
    __functor = self: ctx:
      if config.meta.foo == "bar"
      then { } # do nothing, skip.
      else {
        includes = lib.filter (i: someCondition i) self.includes;
      };
  }
```

Beyond freeform metadata, `meta` carries pipeline-meaningful fields —
`handleWith` (constraints: exclude/substitute/filter aspects in the
subtree), `collisionPolicy` (flat-form class modules), and
`guard`/`aspects` (conditional aspects). See
[Structural Introspection & Constraints](/explanation/structural-introspection/)
and the [aspects reference](/reference/aspects/#metahandlewith).

## Aspect Custom Submodule

In case an aspect needs a custom submodule, it can be added this way:

```nix
# User aspect `tux`
den.aspects.tux =
  { config, ... }: # The function-args style is required for `imports` not to be interpreted as an Aspect class.
  {
    imports = [
      {
        options = {
          default-key = lib.mkOption {
            type = with lib.types; str;
          };
          keygrip = lib.mkOption {
            type = with lib.types; str;
          };
        };
      }
    ];

  default-key = "Hello World!";
  keygrip = "Hello World!";
}
```

And then, you can refer to `tux` aspect from other aspects:

```nix
{ den, ... }:
{
  den.aspects.igloo = {
    homeManager =
      { config, ... }:
      {
        programs = {
          gpg = {
            enable = true;
            settings.default-key = den.aspects.tux.default-key; # Access the `tux` aspect statically
          };
        };

        services = {
          gpg-agent = {
            enable = true;
            enableSshSupport = true;
            sshKeys = [
              den.aspects.${config.home.username}.keygrip # Access the current user aspect dynamically
            ];
          };
        };
      };
  };
}
```

## Aspect Fixed-Point

Aspects are fixed-point, meaning that they can reference themselves, as such:

```nix
{
  den.aspects.igloo =
    {config,...}: # Here, `config` represents the aspect `igloo` itself.
    {
      meta = {
        default-key = "Hello World!";
      };

      homeManager = {
        programs = {
          gpg = {
            enable = true;
            settings.default-key = config.meta.default-key;
          };

          git = {
            enable = true;
            settings.signing.key = config.meta.default-key;
          };
        };
      };
    };
}
```
